    The round above uses test coins. There is also a small round paid in real ZEC on Zcash mainnet: lot IMANI-M1, 3 bids and 3 refunds, with the bids adding up to 0.013 ZEC. The check reads every block from 3,532,593 to 3,532,653 (482 transactions) and passes 23 of 23 checks.

    All 3 bids came from one wallet we ran, and we ran the lot too. So this round shows the checker working on real chain data. It does not show independent bidders.     What Imani is

    Imani is a Zcash library and command line. It reads shielded payments with librustzcash, Zcash's own code, built to WebAssembly so it runs right here in your browser. It checks a whole round from one read-only viewing key plus public chain data, and its command line can download every block from two independent block servers that must agree.

    This page puts it to work on one question: was this sealed-bid auction on Zcash run fairly? It works the result out again from the seller's own files. It runs in your browser and uploads nothing.

    • Finds bids the seller left out. It reads every block of the auction, not only the payments the seller lists.
    • The bidder picks the refund address. It is written in the bid memo on the chain, so the seller cannot swap it.
    • Catches a change to any single number. Alter one bid, refund, winner or price and the check fails, naming the check that caught it.
    • Can re-read the chain from two separate operators. The command line tool downloads every block again and accepts it only when both agree.

    Servers contacted: none. This page makes no network calls after it loads. Your files stay on your device.

    1. Pick something to check

    The page opens on a real auction: a real Zcash wallet paid these bids and refunds on the public Zcash test network. Test coins have no value. Its lot name, DRY-01, stands for dry run: a real round paid with test coins before any real money.

    Made-up rounds, one cheat at a time

    These are built offline with throwaway keys. Each tampered copy changes one thing and fails on exactly the check built to catch it. The stories name the made-up bidders: Alice bids 3,000,000 zat, a second bidder 2,000,000, Carol 1,500,000, and Dave sends 1,200,000 after the close.

    Try a tampered copy: pick the honest round or any of the 6 tampered copies.

    With a full scan of every block

    The scan also reads every block of the auction from a saved copy of the chain, so a payment the seller left out cannot hide.

    With a refund address for every bid

    The seller lists the address each bid's refund must go to. The check reads where each refund really went and compares.

    With the refund address written by the bidder

    Each bidder writes their own refund address at the end of their bid memo, so the seller cannot choose it. The check reads it from the chain and compares it with where each refund went.

    Beyond auctions: a fundraiser or group buy

    The same check works on any collection where the amounts stay hidden. Here the rule is a goal: if the payments reach it they are all kept, and if not every payment is refunded in full.

    Sealed lots: the seller cannot read the prices

    In a plain lot the seller holds the key and could read every bid as it arrives. In a sealed lot each bidder pays the same deposit with only a hash of their price in the memo, then opens it after the close. The check verifies every opened price against its seal, applies the same price rule, and refunds deposits, with a penalty for seals that were never opened.

    Another price rule: the lowest winning bid

    A seller can choose what winners pay. By default it is the highest bid that lost. In this lot it is the lowest bid that won, so the last bidder in pays exactly what they bid. The lot's published rules say which one applies, and the check refuses a result that uses the other.

    Headline numbers a seller publishes

    Big auctions are reported as a few totals: how many bids, how much came in, how much was kept and how much went back. When a seller publishes them in the result file, the check adds them up (received = kept + refunded), compares them with the winners and the refund list, and with the chain.

    2. Result

    Amounts are in zatoshis, the smallest unit of ZEC: 100,000,000 zatoshis make 1 ZEC, so 2,000,000 zat is 0.02 ZEC. How many checks run depends on what the files allow. 5 basic checks need no key. The lot key adds 10, plus 1 when refund addresses are known. Reading every block adds 5, and bidders' own keys add 1.

    A round someone else published

    Drop a round file published by another sealed-bid auction project on Zcash, or try one of the three below. The page works the numbers out again under that file's own rules. It reads only what is in the file and does not look at the chain.

    Where each number comes from

    From the chain

    Bid amounts, bid memos, refund amounts and refund memos. Read from the lot's transactions with the lot's one-time viewing key. Transaction ids are recomputed from the bytes.

    From the seller's file

    The bid list, winners, clearing price, reserve outcome and refund list the seller claims. The checker works these out again and compares.

    From the disclosure file

    Close height, the block height of each transaction, item count and reserve. Without the scan level these heights are taken on the seller's word.

    What this check cannot do

    • It only works when the seller shares the lot's one-time viewing key. A viewing key shows payments and can never spend them. Without it only the basic checks run.
    • The seller can see bids as they arrive. The check proves that the counting, amounts, price and refunds are right. It does not prove the seller never looked.
    • This is not a zero-knowledge proof. You recompute the result yourself from data the seller chose to share.
    • A shared viewing key cannot be taken back. Anyone who has it can see that lot's payments for good, so each lot needs its own fresh key.
    • Without the scan level, block heights and the list of payments come from the seller's files. With it, a saved chain file covers every block, but you still trust where that file came from.
    • A refund is shown to have left the lot with the right amount. Where it went is compared with the refund address the bidder wrote in their bid memo, which the seller cannot choose, or else with the list the seller gives. A seller's list is the seller's word: each bidder should check the address next to their bid is theirs. A refund is shown to have reached the bidder for certain only when that bidder supplies their own viewing key.

    About your files and keys

    • Nothing is uploaded. The page has no code that talks to a server, and its security policy forbids it (connect-src 'none').
    • Keys are checked on this device. Seed phrases and spending keys are refused. The lot key is never shown on this page.
    • Nothing is saved in cookies or browser storage. Close the tab and it is gone.
